> **实测状态**：2026-11-10 在 **106.52.73.17（生产）** 与 **45.76.84.90（法兰克福预发）** 两台真机验证。

## 0. 在哪台机器上执行（v2.1 强制，先看这条）

| 命令 | 允许的执行位置 | 说明 |
|---|---|---|
| `preflight` / `infra` / `secrets` / `verify` | **只在目标 Linux 机**（106 / FRA） | 读本机的用户、`/etc/os-release`、端口、systemd；在 Mac/Win 上跑没有意义 |
| `render` | 任意机器 | 纯文本替换，不碰本机；非 Linux 上自动进入离线模式 |

在非 Linux 主机上跑前四个命令，会直接 `FATAL ... 当前主机是 Darwin，不是目标机` 并 `exit 3`，不再拿「用户不存在：ubuntu」这种误导性报错冒充演练失败。

> **v2.2 及以前在 Mac 上其实到不了这句**：`echo "...$HOST_OS，..."` 里那个全角逗号会被 **bash 3.2**
> 当成变量名的一部分（3.2 不做多字节解析），`set -u` 下直接 `HOST_OS: unbound variable`，**退出 1**。
> v2.3 把全脚本 30 处「变量紧跟中文/全角」的展开统一改成 `${VAR}`，并把 `HOST_OS` 的取值加了默认兜底。
> `render` 之所以一直没事，是因为它不经过那句 echo。

**升级到 v2.3 后，先在 Mac 上跑一次自检**（只读 + 临时目录，不碰本机、不碰线上）：

```bash
bash tests/selfcheck.sh          # 期望末行：全部通过（8 项）
```

它验的就是这次踩到的那类问题：四条命令在非 Linux 上必须 `exit 3`、`render` 必须能离线跑、
`kit.conf` 与命令行的优先级、以及「有没有变量紧跟中文」这个静态判据。

在 Mac 上只做配置校对：

```bash
./bootstrap.sh render --offline --user=ubuntu --base=/home/ubuntu \
    --looma-port=5200 --core-port=5300 --gfcc-port=5211 --take-default \
    --wp-upstream=45.76.84.90 --out=./rendered
```

> `--offline` 不查用户、不读 os-release，只按参数渲染；`render` 在 `uname != Linux` 时自动开启。

## 0.1 职责三分（谁装什么）

| 层 | 谁负责 | 内容 |
|---|---|---|
| **CI（3 条流水线）** | 自动 | 代码 clone/rsync、release 切换、venv 与钉版依赖、smoke 门禁、重启单元、覆盖 `looma.conf` |
| **bootstrap.sh（本套件）** | 一次性 | OS 包、目录、systemd 单元 + drop-in、nginx 站点、ufw 提示、`.env` 骨架与七键奇偶校验 |
| **人工** | 一次性 | 外部凭据填 `.env`、云防火墙规则、GitHub secrets、DNS |

原则：**CI 不写凭据，bootstrap 不碰代码，人工不碰机器内可自动化的东西。**

## 1. 环境矩阵（先看这张表，别照抄参数）

两台机器的差异不是细节，是参数源。**v1 把 106 的快照当通用配置，所以在第二台机上必炸**——这是 v2 存在的唯一理由。

| 项 | 106 生产（腾讯云） | FRA 预发（Vultr） |
|---|---|---|
| OS | Ubuntu **22.04.5** LTS (jammy) | Ubuntu **22.04.5** LTS (jammy) |
| Python | **3.12.16**（deadsnakes PPA） | 系统 3.10.12；容器内 3.12.15 |
| 登录用户 | `ubuntu`（uid 1000） | `root` / `linuxuser`（uid 1000, sudo） |
| 应用形态 | venv + systemd | **docker compose**（looma/tatha/pg×2/redis/chroma）+ 1 个 systemd（gfcc） |
| 已占端口 | 5200 / 5300 / 5211 / 80 | **5200(docker) / 5204 / 5210 / 5211(gfcc) / 5433 / 5434 / 80 / 443** |
| nginx default_server | looma（本套件抢） | **nginx 自带 default 页（不能抢）** |
| `/wp-json` 上游 | 45.76.84.90（= FRA 那台的书店） | **无（留空，否则自己反代自己）** |
| ufw | 开：22/80/443/5300 | 开：22/80 |
| 公网边界 | 腾讯云安全组（5300 已关） | Vultr Firewall |
| 端口绑定 | 5200、5211 只听 `127.0.0.1`；**5300 是 `0.0.0.0`**（`run_core.py` 未改绑） | 同左（docker 另占） |

**两个由此推出的硬结论：**

1. **106 是 Ubuntu 22.04，不是 24.04**。python3.12 靠 deadsnakes 后装。任何新开 22.04 机器都必须先加 PPA，否则 CI 的 venv 建不起来。
2. **`--wp-upstream` 是环境专属值**。106 上填 `45.76.84.90`；在 FRA 本机必须**留空**，否则 `/wp-json` 会把请求反代给自己，nginx 起得来但请求打转（500/超时）。

## 2. 参数表

所有参数都可用命令行给，也可写进 `kit.conf`（复制 `kit.conf.example`，不进 git）。
优先级：**命令行 > kit.conf > 内置默认**。

> v2.2 起这条优先级才真的成立：`kit.conf` 在参数解析**之前**加载，命令行随后覆盖它。
> v2.1 及以前加载在解析之后——`kit.conf.example` 用的是裸赋值，于是「写在后面、执行在前面」，命令行被静默盖掉且无任何提示。
> 106 上因没有 `kit.conf` 所以从未触发；从 FRA 拷一份过去会改了端口却看不出来。已修，并加了单测（见 §5.5）。

| 参数 | 默认 | 说明 | 106 取值 | FRA 演练取值 |
|---|---|---|---|---|
| `--user=` | 自动（ubuntu > uid1000 > 当前） | 运行用户；决定家目录与 `User=` | `ubuntu` | `linuxuser` |
| `--base=` | 该用户家目录 | 应用根目录 | `/home/ubuntu` | `/home/linuxuser` |
| `--looma-port=` | 5200 | 宿主端口（gunicorn 只听 127.0.0.1） | 5200 | **6200** |
| `--core-port=` | 5300 | 核端口 | 5300 | **6300** |
| `--gfcc-port=` | 5211 | GFCC 端口 | 5211 | **6211** |
| `--unit-prefix=` | 空 | 单元名前缀，用于与既有服务隔离 | （空） | **`shadow-`** |
| `--wp-upstream=` | 空 | 门户 `/wp-json` 上游；空=整段不渲染 | `45.76.84.90` | （空） |
| `--portal-root=` | `/var/www/szbolent.com/dist` | 门户静态目录 | 默认 | `/tmp/shadow-portal` |
| `--python=` | 3.12 | 目标解释器版本 | 3.12 | 3.10（--no-ppa 时自动降级） |
| `--no-nginx` | — | 完全不碰 nginx | — | ✅ 用 |
| `--take-default` | — | 允许抢占 80 default_server 并摘除 `sites-enabled/default` | ✅ 用 | **绝不用** |
| `--no-ppa` | — | 禁止添加 deadsnakes PPA | — | 演练时用 |
| `--dry-run` | — | 只打印动作，不落盘 | 预演时用 | ✅ 先用 |
| `--offline` | — | 不查本机用户/os-release，只按参数渲染；`render` 在非 Linux 上自动开 | 不需要 | Mac 上校对时用 |
| `--force` | — | 端口/单元冲突时不中止 | 慎用 | 慎用 |

## 3. 从零到一：五步

```
开机（Ubuntu 22.04/24.04，云防火墙只开 22/80/443）
  → ⓪ sudo ./bootstrap.sh preflight        ← 先体检，什么都不改
  → ① ssh key + 授权 CI
  → ② sudo ./bootstrap.sh infra
  → ③ ./bootstrap.sh secrets（生成内部密钥；人工补外部凭据）
  → ④ 触发三条 CI 首次部署
  → ⑤ ./bootstrap.sh verify 全绿 → 交接运维手册
```

### ⓪ preflight（新增，务必先跑）

```bash
# 先把套件送上目标机——这一步不能省，preflight 只在目标机上才有意义
scp 106-deploy-kit-v2.2.zip ubuntu@<IP>:~/
# Linux 的 unzip 会把中文文件名解成乱码，用 python 的 zipfile 保真
ssh ubuntu@<IP> 'python3 -m zipfile -e ~/106-deploy-kit-v2.2.zip ~/ && cd ~/106-deploy-kit && chmod +x bootstrap.sh'
ssh ubuntu@<IP> 'cd ~/106-deploy-kit && sudo ./bootstrap.sh preflight'   # 0=可继续，2=有阻断项，3=站错机器
```

它会报告：OS 与 python 可得性、**三个端口是否被别的服务占着**、nginx 是否已有 default_server、已有同名单元是否属于别的栈、磁盘余量、drop-in 是否已接管 env 清单。**只读，不改任何文件。**

> 退出码 **3 = 你在非 Linux 主机上执行**（比如 Mac 本机）。这不是机器有问题，是站错了地方，`ssh` 到目标机再跑。

### ① SSH 与 CI 授权

```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_<新机名>
ssh-copy-id -i ~/.ssh/id_ed25519_<新机名>.pub ubuntu@<IP>

# CI deploy key（thomas-core 用只读 deploy key 拉 GitHub）
ssh-keygen -t ed25519 -f ~/.ssh/deploy_thomas_core
cat ~/.ssh/deploy_thomas_core.pub >> ~/.ssh/authorized_keys   # 公钥另一份贴进 GitHub Deploy keys
```

looma-zervi 仓库 secrets：`DEPLOY106_HOST` / `DEPLOY106_USER` / `DEPLOY106_SSH_KEY` / `DEPLOY106_HOST_FINGERPRINT` 换成新机。
**注意**：workflow 读 `vars.X || secrets.X` 两种放法都吃，但**不要只建成 Secret 而 workflow 只读 vars**——这个坑已经踩过一次。指纹用 `ssh-keyscan -t ecdsa <IP> | ssh-keygen -l -f -`。

`DEPLOY106_USER` **可以不建**：thomas-core 的 `scripts/ci-ssh.sh` 是 `user="${DEPLOY106_USER:-ubuntu}"`，空值兜底 `ubuntu`。
实测两个仓都没有这个变量，部署照常成功。真正会挡住的是 `HOST` / `SSH_KEY` / `FINGERPRINT` 三项，缺哪个 workflow 会点名报错。
（推论：新机登录用户不是 `ubuntu` 时，这项**必须**建，否则会用错用户名。）

### ② infra

```bash
sudo ./bootstrap.sh infra --user=ubuntu --base=/home/ubuntu --take-default --wp-upstream=45.76.84.90
```

装：nginx / rsync / sqlite3 / openssl / curl / ca-certificates / tcpdump + **python3.12**（22.04 自动加 deadsnakes，24.04 直装，拿不到就降级并告警）。
建：`looma|thomas|gfcc-kernel` 的 `data/logs/bin`、门户 dist、certbot 目录。
装：4 份 systemd 文件（含 `ledger.conf` drop-in）、2 个 nginx 站点。
**单元只 enable 不 start**——代码还没来。

`infra` 是幂等的：内容没变就完全不动文件（不堆 `.bak`）。但**首次在一台已按 v1 部署的机器上跑**，会因 `EnvironmentFile=-` 前缀与注释更新 6 个文件，属预期改进，自动备份。

### ③ secrets

```bash
./bootstrap.sh secrets --user=ubuntu
```

- **共享密钥只在宿主生成**：`SECRET_KEY` / `JWT_SECRET` / `ETHOS_AUTH_SECRET` → 其余两份用 `copy_key` 抄过去，末尾哈希奇偶校验，`PARITY_OK` 才放行。
- **各文件私有键自生成**：gfcc 的 `SIGNAL_INGEST_SECRET`。
- **人工填**（缺失只降级不阻断）：`DEEPSEEK_API_KEY`、`WECHAT_APPID/APP_SECRET`（APPID=`wx842b6837e6898789`、`DEV_MODE=false`）、`QCC_AUTH_TOKEN`、`HUAWEI_CLIENT_ID/SECRET`。

> ⚠️ v1 的致命 bug：三份 `.env` 各自 `openssl rand`，`JWT_SECRET` 必然三份不同，`PARITY_FAIL` 必现。v2 已改为一处生成、两处抄。

### ④ 触发三条 CI

looma-zervi（deploy-106）、thomas-core（deploy-106）、gfcc（经 thomas-core CI 伴生部署）。部署脚本自己 clone、建 venv、钉版装依赖、smoke 9/9、切 current、重启单元，并写 `deploy.env` 的 `GIT_COMMIT`。

**顺序必须是「核 → 宿主」，不能反过来。** 新宿主调旧核 = 宿主用了核还没实现的接口，最坏是新 looma 打 500；
新核配旧宿主 = 核多几个没人调用的接口，无害。gfcc 是 thomas-core 那次部署连带拉起的，所以实际只有两条流水线，
顺序是 `gfcc 契约 → 核 :5300 → 宿主 :5200`。`deploy-orchestrator` 的 `deploy-all.yml` 已按这个顺序钉死。

### ⑤ verify

```bash
./bootstrap.sh verify --user=ubuntu
```

四单元 active、`:5200` `ok`、`:5300` `ok`、`:5211` `ok`、门户 200、闭环探针 `invalid code`。
**它不会假绿**：单元没起、端口不通、探针返回空，都会明确报出并退出 1。

## 4. 共存模式（在已有服务的机器上新增实例）

预发机这类场景：机器上已经跑着别人的栈。**直接照 106 参数跑会打挂现有服务**，必须做四件隔离：

| 隔离维度 | 做法 | 不隔离的后果 |
|---|---|---|
| **端口** | `--looma-port=6200 --core-port=6300 --gfcc-port=6211` | 与 docker 的 5200、既有 gfcc 的 5211 撞车，起不来 |
| **单元名** | `--unit-prefix=shadow-` | 覆盖在跑的 `gfcc-kernel.service`（它指向 `/data/gfcc`） |
| **目录** | `--base=/home/linuxuser`（或另一个用户） | 写进别人的 `~/looma` |
| **nginx** | `--no-nginx` | `rm sites-enabled/default` 会摘掉现有站点；抢 default_server 会让 `nginx -t` 报 duplicate 并连带改坏 |
| **门户目录** | `--portal-root=/tmp/shadow-portal` | 覆盖 `/var/www` |

```bash
sudo ./bootstrap.sh infra \
  --user=linuxuser --looma-port=6200 --core-port=6300 --gfcc-port=6211 \
  --unit-prefix=shadow- --no-nginx --no-ppa --portal-root=/tmp/shadow-portal
./bootstrap.sh secrets --user=linuxuser --looma-port=6200 --core-port=6300 --gfcc-port=6211 --unit-prefix=shadow- --no-ppa
./bootstrap.sh verify  --user=linuxuser --looma-port=6200 --core-port=6300 --gfcc-port=6211 --unit-prefix=shadow- --no-nginx
```

**防御是默认开着的**，不靠人记得：

- 端口被非本套件进程占着 → `preflight` 阻断（退出码 2）
- 同名单元但 `WorkingDirectory` 指向别处 → `infra` 拒绝覆盖并中止
- 已有 `default_server` → 本套件站点自动降级为普通 `listen 80`
- nginx `-t` 失败 → 自动回滚到备份

## 6. 密钥灾难恢复（DR）

三份 `.env` 是全机唯一凭据存放点，CI 不写、git 不存。丢机器 = 丢凭据。

| 路线 | 做法 | 代价 |
|---|---|---|
| **A. 加密备份（推荐）** | 每次改 `.env` 后 `age -p -o <host>-env.age`（三合一 tar），密文存私有仓或你的 Mac；恢复 = 解密放回 | 改一次备一次，5 分钟 |
| **B. 全新生成** | 重跑 `secrets` + 人工找回外部凭据 | 内部密钥全换 → 所有登录态失效、桥接 secret 重配 |

无论哪条，**都不要把明文 .env 存进仓库、聊天或工单**。

## 7. 已知限制（别指望脚本做）

1. **不在云控制台改防火墙**——腾讯云安全组 / Vultr Firewall 要人工操作。`ufw` 只做只读检查，不擅自放行端口。
2. **不建 venv、不装 pip 依赖**——那是 CI 的事，脚本只保证解释器可用。
3. **`verify` 需要 CI 部署完成**。首次 `infra` 后直接 `verify` 必然报「单元未运行」，这是正确行为。
4. **python 3.12 在 22.04 上依赖 deadsnakes**。若目标机禁第三方 PPA，只能用 3.10，需自行确认代码兼容性（looma 现按 3.12 开发）。
5. **`run_core.py` 仍绑 `0.0.0.0`**（106 上）——公网边界靠安全组，代码层改绑 127.0.0.1 属后续加固。
6. **门户 dist 仍是手动/CI 外发布**。
7. **`nginx/looma.conf` 的真源在 looma-zervi 仓**（CI 每次覆盖）。本套件模板只用于新机首次引导；两处漂移以仓内为准。
8. **looma-backend 与 gfcc-kernel 的主单元会被各仓部署脚本重写**（thomas-core 不重装）。所以单元里那两条顺手加上的设置（`EnvironmentFile=-` 前缀、`Environment=GFCC_PORT=`）**下次 CI 就没了**——它们已改放 drop-in `zz-kit.conf`，CI 不动 drop-in，因此能留下。thomas-core 的 `ledger.conf` 同理。
   ⚠️ 代价：drop-in 里第一行 `EnvironmentFile=`（空赋值）会**清空主单元的 env 清单**再由 drop-in 重列。若 CI 日后给某个单元新增一个 env 文件，必须同步加进 `systemd/zz-kit.conf.in` 的清单，否则会被静默丢掉。
9. **门户只渲染 `listen 80`**，不写 443。证书用 certbot 单独签，443 server 块属人工/后续步骤；模板里保留 `@CERTBOT_ROOT@` 只用于 webroot 续期路径。
10. **`verify` 的闭环探针要读核日志**（`$THOMAS_DIR/logs/thomas-core.log`），且需要读该文件的权限（`sudo`）。判据是两层的：
    ① 核日志里出现探针串 `bootstrap-probe-<ts>` → 最硬；
    ② 探针之后核日志新增一条 `POST /v1/auth/wechat`（400）→ 说明这次调用确实落到核并被处理。
    **已知局限**：核目前只记 werkzeug 访问日志、不记请求体，所以 ② 只能证明「同一时刻这次调用到了核」，不能逐字对上探针串。要逐字对上，得让核把入参记进日志（属代码改动，未做）。
    两层都不成立（探针后核日志毫无新增）就判失败——这正是 v2.0 假绿的场景：宿主自己回 `invalid code`，核其实没收到。
11. **`kit.conf` 覆盖命令行**（v2.1 及以前的 bug，v2.2 已修）：`kit.conf` 曾在参数解析之后加载，裸赋值会静默盖掉命令行。
    现在加载在解析之前。若你在旧版上放了一份 `kit.conf`，升级后行为会变（这才是手册承诺的那个优先级）。
12. **`make_dirs` 只保证 `data/logs/bin` 的属主**（v2.2 起新增父目录处理）：空机器上父目录若仍是 `root:root`，
    CI 以 `$APP_USER` 建 `releases/current` 会 `Permission denied`，表现为「infra 全绿、第一次部署必挂」。
13. **`verify` 的账本断言依赖 `MainPID`**：单元没在跑时读不到 `/proc/<pid>/environ`，会退回单元声明；
    两处都读不到才判失败。它验的是「核进程实际用的库」，不是「配置里写的库」——两者不一致时，报的是前者。
14. **bash 3.2 不做多字节解析**（v2.3 已修，但写补丁时要注意）：`$VAR` 后面紧跟中文或全角标点时，
    3.2 会把那几个高位字节当成变量名的一部分，`set -u` 下直接 `unbound variable`。脚本内已统一写成 `${VAR}`；
    `tests/selfcheck.sh` 里保留了静态判据，改脚本后跑一次就能发现回归。
15. **`BOOTSTRAP_HOST_OS` 是测试钩子，不是配置项**：设了它就会覆盖 `uname -s`，用于在 Linux 上回归「站错机器」分支。
    正常运行不要设它，否则守卫会被骗过、在错误的主机上继续往下跑。
